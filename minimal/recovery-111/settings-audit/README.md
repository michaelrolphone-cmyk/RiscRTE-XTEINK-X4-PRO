## Persistence behavior and remaining limits

Successful connection remembers each SSID independently; edits to an existing SSID update its profile. A native atomic commit queues durable synchronization intent. The bounded owner/worker lifecycle publishes and verifies a complete SD checkpoint before acknowledging it. Ordinary paired updates preserve native storage. A full-initial image overwrites NVS/app-data: restoration then depends on the retained, acknowledged SD checkpoint. A just-saved edit erased before that checkpoint finishes can be lost. Do not describe a native save receipt as proof of SD completion.

Cold native storage with an absent, ambiguous or conflicting SD source stays unavailable; it does not persist temporary defaults. Clean restoration waits for namespace data-grant release. Temporary edits remain drafts until explicitly resolved. Existing initialized native settings remain usable without a card, with pending synchronization preserved. Conflicting independent datasets are preserved rather than silently merged.

Physical card removal/reinsertion, actual full-flash recovery, scheduler/heap limits and radio association across reboot remain hardware qualification items. No device was flashed, no release was published, and the prepared .111 delivery was not replaced.
